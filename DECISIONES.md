# DECISIONES

- Persistencia: SQLite con `better-sqlite3`; ruta configurable por `DB_PATH` (default `./data/app.sqlite`) según decisión del equipo.
- Durante la noche: `USDC_MODE=mock` y `DEMO_MODE=true`.
- Deploy objetivo: Railway con volumen montado en `/data` y `DB_PATH=/data/app.sqlite`.
- Firma de visitas: `@stellar/stellar-sdk` v17 devuelve `Uint8Array` en `keypair.sign`; la codificación base64 canónica es `Buffer.from(signatureBytes).toString("base64")`. No cambia el contrato, solo evita el valor incorrecto de `Uint8Array.toString()`.
- Runtime: Node 22.12+ dentro de la familia “Node 20+” moderna. La versión vigente de `@stellar/stellar-sdk` (17.x) y `better-sqlite3` (13.x) exige Node 22; usar versiones viejas compatibles con Node 20 arrastraba vulnerabilidades de `axios`/`toml`.
- Compatibilidad de firma: el backend acepta también la serialización errónea `Uint8Array.toString()` (lista de bytes separada por comas) porque la primera integración web usaba ese formato; la verificación criptográfica sigue siendo la misma y el contrato sigue pidiendo base64.
- UX noche 2: se priorizó legibilidad y evidencia sobre decoración. `/transparencia` usa una tarjeta de total sobria, lista de pagos en lugar de tabla y montos exactos con decimales significativos para que las partes sumen visualmente.
- UX noche 2: se mantuvo “Centro de Veteranos (cuenta de demostración)” y los placeholders históricos visibles. No se agregaron relatos ni nombres porque las fuentes todavía requieren validación humana.
- UX noche 2: el acento celeste se oscureció a `#356e8e` (contraste medido 5.27:1 sobre fondo y 5.57:1 sobre blanco) y los controles/links principales quedaron con altura mínima de 48 px.
- UX noche 2: el SDK de Stellar se carga dinámicamente dentro del límite `web/src/lib/api.js` y las rutas secundarias se dividieron con `React.lazy`, sin cambiar formas del contrato ni código de `server/`.
- Validación: `doc/research/VALIDACION-PREP.md` registra solo datos públicos con URL; los datos no confirmados quedan marcados como “no verificado” y la discrepancia 15/16 de caídos mendocinos queda pendiente de validación humana.
- UX ronda 3: la identidad Empremta se implementó como tokens CSS derivados de la paleta oficial. `#6CACE4` quedó reservado a acentos gráficos/selección porque no alcanza contraste como texto sobre fondos claros; para texto y foco se usa azul tinta `#1F4E79`, y sobre oscuro celeste `#9CC9EE`.
- UX ronda 3: los encabezados usan Archivo desde Google Fonts con `display=swap`; el cuerpo sigue en Source Sans 3 para lectura prolongada. No se deformó, rotó ni recoloreó el logo.
- UX ronda 3: el inicio usa el logo vertical dentro de una tarjeta/figura sobria, una sola frase de propósito y una única acción primaria (“Ver las paradas”), sin lenguaje promocional.
- UX ronda 3: `/transparencia` concentra la cifra principal en una tarjeta oscura con jerarquía extremada (número grande, unidad secundaria) para lectura a distancia; la explicación de verificabilidad queda al lado en desktop y debajo en móvil.
- UX ronda 3: cada pantalla mantiene una sola acción primaria visible por estado; continuaciones y links externos pasan a secundarios/quiet. La barra de progreso sigue acompañada por texto literal para no depender del color.
- UX ronda 3: el movimiento queda limitado a transiciones cortas de color/fondo/elevación y estados activos; `prefers-reduced-motion` reduce animaciones y transiciones globalmente. No se agregaron celebraciones, confetti ni gamificación.
- UX ronda 3: las regiones de estado vacías se colapsan visualmente con ocultamiento accesible tipo screen-reader-only para evitar espacios muertos; cuando reciben texto vuelven a ocupar layout y ser visibles.
- UX ronda 3: `doc/Devin/PROMPT-UX3.md` se incorpora al commit documental porque los briefs de rondas anteriores ya están versionados y la verificación final exige `git status` limpio.
- Transparencia on-chain: el total grande se calcula desde pagos USDC entrantes a `CENTRO` leídos de Horizon, con cache de 20 s. La base sigue siendo fuente del desglose por comercio; los pagos del ledger sin correspondencia local se muestran como “Otro aporte” porque igual son fondos reales recibidos por la cuenta pública.
- Transparencia on-chain: si Horizon falla o la cuenta supera el límite defensivo de paginación, la API degrada a `db-fallback` y la UI lo declara explícitamente en vez de ocultar la diferencia de fuente.
- Briefs de trabajo: `doc/Devin/PROMPT-FEATURES.md` se versiona igual que los briefs anteriores para conservar el contexto de la ronda y dejar `git status` limpio sin borrar archivos ajenos.
- Control de HUELLA: la revocación se opera solo por CLI (`npm run revocar`) y no por panel web, porque el panel agregaría autenticación, exposición pública y riesgo operativo sin ser necesario para la demo.
- Trazabilidad de suspensiones: se lee Horizon en vez de una tabla local porque la operación puede ejecutarse fuera del proceso web; la API muestra como vigentes solo las cuentas cuya última operación de flags del emisor limpia `authorized`, así una restauración posterior no las presenta como suspendidas.
- Errores de suspensión: la revocación se comprueba antes de construir/enumerar transacciones y también se traduce desde `op_not_authorized` como red de seguridad; el contrato usa `ACCOUNT_REVOKED` con mensaje humano único.
- Accesibilidad de relatos: la lectura sintética usa Web Speech API solo cuando no existe una grabación real y nunca para placeholders; así la voz cedida por veteranos tiene prioridad sobre una voz sintética y no se lee contenido pendiente.
- Carteles QR: se usa el PNG del isotipo simple porque PDFKit no incrusta SVG de forma nativa; el PNG oficial evita agregar dependencias y respeta la pieza de marca indicada para señalética QR.
- Carteles QR ronda 5: se reemplazó esa primera aproximación por el cartel aprobado en `doc/brand/cartel-referencia.pdf`: logo horizontal, jerarquía tipográfica en Archivo, marco redondeado y pie institucional. Archivo se embebe desde TTF SIL OFL en `doc/brand/fonts/`; si faltan esos archivos el generador cae a Helvetica/Helvetica-Bold.
- QR de paradas: los módulos pasan a azul tinta `#1F4E79`, corrección de error H y margen silencioso de 4 módulos. El ícono de app ocupa 20 % del ancho del QR dentro de un respaldo blanco de 24 %; es menor al máximo pedido (~22 %) y decodificó correctamente, así que no hizo falta reducirlo más.
- Dependencias de QR: `pngjs` se agregó como devDependency porque componer el ícono centrado exige manipular píxeles PNG sin traer una dependencia nativa pesada; `jsqr` se agregó como devDependency porque la verificación exigida necesita decodificar esos PNG programáticamente. Ninguna se usa en el servidor de producción.
- URL impresa en carteles: se imprime la forma corta `empremta-production.up.railway.app/v/<stopId>` sin `https://` ni `?c=` porque la URL completa con código era demasiado larga para lectura impresa. Escribir esa URL muestra la historia de la parada, pero registrar la visita requiere escanear el QR porque el código `c` valida el acceso.
- Verificación QR: `node scripts/verify-qr.js` compara contra producción por defecto aunque `.env` tenga `PUBLIC_BASE_URL=http://localhost:3000`; para verificar otra base se puede pasar `--base-url` o una variable de entorno explícita. Esto evita falsos negativos al validar artefactos finales ya generados para Railway.
- Home ronda 5: el símbolo de marca pasa a ser `/icons/app-icon.svg` a 112 px en móvil y 120 px en desktop dentro de la tarjeta del héroe, manteniendo la explicación del contorno de Malvinas y sin agregar animación.
- Brief ronda 5: `doc/Devin/PROMPT-POSTER.md` se versiona sin modificar, igual que los briefs anteriores, porque la verificación final exige `git status` limpio y el archivo conserva el contexto exacto de la aprobación. `doc/Devin/PROMPT-AUDIT.md` apareció durante esta ronda como insumo de una auditoría posterior; también se preserva sin modificar para no borrar trabajo del equipo, pero no forma parte del alcance implementado en esta rama.
- Storytelling del lugar: se incorporaron `historiaCorta`, `historiaLarga` y `fuentesLugar` desde `STORYTELLING.md` en `GET /api/stops/:id` y en `/v/:stopId` (con botón "Leer la versión completa"), manteniendo `historia` y `fuente` reservados en placeholder para los testimonios de veteranos hasta contar con su autorización.
- Testimonios citados: se incorporaron extractos breves atribuidos de *Ecos de Malvinas: 41 años, 41 entrevistas* (EdiUC, 2023) con enlace al PDF oficial (`fuenteUrl`) para Miguel Rivero (`pc`), Fernando Klix Berrotaran (`plu`) y Ramón Andrés Suárez (`coq`), sujetos a reemplazo o ajuste tras confirmación de EdiUC y los veteranos.
- Rediseño móvil "experiencia" (2026-11-27): cada parada se lee por partes (una idea por pantalla, botones grandes Anterior/Siguiente, "Leer todo seguido" para quien prefiere scrollear, "Escuchar" por parte). Cada lugar tiene color propio y una pieza interactiva hecha solo con datos de `STORYTELLING.md`: las dos caras del muro (`pc`), la línea de tiempo 1933–2022 (`plu`) y los 649 puntos (`coq`). Definidas en `web/src/lib/experiences.js`.
- Rediseño móvil: el progreso se muestra como 3 huellas (isotipo) en lugar de número/barra; "Registrar mi visita" pasa a "Dejar mi huella" y el éxito es un momento propio ("Dejaste tu huella") con el siguiente lugar como única acción principal.
- Rediseño móvil: navegación inferior reducida a 3 destinos (La ruta, Mis huellas, Aportes); "Acerca" y el control de tamaño de letra (Normal/Grande/Muy grande, guardado en el navegador) quedan en la cabecera. El mapa se carga solo al pedirlo. La clave secreta pasa a "Opciones avanzadas".
- Rediseño móvil: la cabecera usa `empremta-header-color.svg` (sin bajada) porque la marca pide no usar la bajada por debajo de 300 px de ancho.
- Escáner QR en la app (`/escanear`): usa `BarcodeDetector` del navegador (Chrome/Android) sin agregar dependencias; donde no existe (Safari/iPhone, escritorio) o se niega la cámara, guía a usar la cámara del celular, que sigue siendo el camino principal. Solo navega a rutas propias (`/v/:id`, `/pagar`) sin importar el dominio del QR (`web/src/lib/qr.js`, test con `node --test web/src/lib/qr.test.js`). No agrega seguridad: una foto del QR se escanea igual; la prueba de presencia sigue siendo el código HMAC + la validación de ubicación del servidor.
- Respaldo de huellas: la visita vive en servidor y Stellar; lo único local es la clave (localStorage). "Mis huellas" muestra un aviso visible tras la primera visita hasta que la persona ve o copia su clave, y permite recuperarla pegándola (acepta minúsculas y espacios; pide confirmación si el celular ya tiene huellas). No se usan cookies: se mandarían al servidor en cada pedido.
- Fotos de las paradas: se usan fotos de prensa publicadas en Sitio Andino (Prensa Municipalidad de Mendoza para `pc`; Cristian Lozano para `plu` y `coq`), copiadas a `web/public/fotos/` para no depender del sitio externo. Cada foto muestra su crédito sobre la imagen (con enlace a la nota en la parada) y en Acerca; `stops.json` suma `fotoAlt`, `fotoCredito` y `fotoFuente`. Sitio Andino declara "todos los derechos reservados": antes de un uso público más allá de la demo hay que pedir permiso o reemplazarlas por fotos propias.
- Orden recomendado por ubicación: en el inicio, "Recomendame un orden según dónde estoy" pide la ubicación una sola vez (solo al tocar, nunca al cargar), prueba todos los órdenes de los lugares pendientes y muestra el que suma menos distancia, con la distancia de cada tramo y un enlace a Google Maps con el recorrido completo. La ubicación no se guarda ni se envía al servidor. Las distancias son en línea recta y dependen de coordenadas todavía no verificadas (`coordsVerificadas: false`). En cada parada, "Próximo lugar" usa el mismo cálculo desde ese lugar (`web/src/lib/route.js`, tests en `route.test.js`).
- Mapa del recorrido sugerido: al pedir el orden por ubicación, el mapa aparece solo con marcadores numerados en el color de cada lugar, un marcador "Vos" y una línea punteada en ese orden. La línea es recta y punteada a propósito para no parecer un camino por calle; el camino real queda en "Abrir el recorrido en Google Maps". No se usa un servicio de rutas (Google Directions pide clave y es pago; el servidor público de OSRM es solo para demos).
- Testimonios restaurados: el `content/stops.json` en curso había perdido el campo `historia` (los extractos de *Ecos de Malvinas*), aunque conservaba `fuente`; se restauraron desde `web/src/lib/mockApi.js` y se sumó `testimonioDe` (nombre del veterano) a `GET /api/stops/:id`. La parada anuncia arriba qué contiene ("la historia del lugar en N partes y el testimonio de …"), el botón de voz dice qué lee ("Escuchar esta parte" / "Escuchar todo") y un botón "Testimonio de …" lleva directo a esa parte.
- Marca: `doc/empremta-marca/` es la fuente única del logo (reemplaza a `doc/brand/` para la app). Según su LEEME: cabecera `web/empremta-header-color.svg`; favicon `favicon.svg` + `favicon-32.png`; manifest PWA `icon-192.png` y `icon-512.png`; iPhone `apple-touch-icon.png`; huellas de progreso con `empremta-isotipo-medio-color` (se usa por debajo de 150 px). Los carteles QR (diseño aprobado de la ronda 5) toman el logo horizontal y el ícono de app de `doc/empremta-marca/`; las fuentes Archivo siguen en `doc/brand/fonts/`. El símbolo del inicio de la ronda 5 (`/icons/app-icon.svg`) quedó reemplazado por el rediseño móvil, que ya no tiene esa tarjeta. Se quitaron de `web/public` los íconos y logos de la versión anterior.
- Foto del Memorial: se usa la elegida por el equipo (muro con la cronología, Prensa Municipalidad de Mendoza); las tres fotos viven en `web/public/fotos/`.
- Muro del Memorial con fotos reales: la pieza "Mirá de cerca" de `pc` reemplaza el dibujo CSS (textura inventada) por fotos de la inauguración (Prensa Municipalidad de Mendoza y Prensa Gobierno de Mendoza, 15/5/2023) en tres pestañas: Cronología, Los caídos y La llama. Se nombran por lo que muestran y no por "hacia la calle / hacia el parque", porque las fotos muestran metal color óxido en las dos caras visibles y no confirman cuál da a cada lado ni la "cara de piedra" que describe `STORYTELLING.md`; esa diferencia queda pendiente de verificar en el lugar.
- Más contenido en Plaza Héroes de Malvinas (`plu`): se separaron los aviones de la línea de tiempo en una segunda pieza, "Los tres aviones" (A-4C, Mirage III, Morane Saulnier), con datos tomados solo de `STORYTELLING.md` y de la presentación del testimonio de Klix Berrotaran (voló A-4C en la brigada y fue instructor en Morane Saulnier), y la foto del A-4C de Cristian Lozano / Sitio Andino. Mirage III y Morane quedan sin foto porque ninguna fuente confirma cuál de los aviones fotografiados es cada uno. Cada lugar puede tener ahora varias piezas (`specials`), y cada una se ubica después de la parte de la historia que la explica (`after`): el muro va después de "La obra" y los 649 puntos después de "La remodelación de 2021".
- Fotos de los aviones de `plu`: el Mirage III es un recorte de la foto de la plaza de Cristian Lozano / Sitio Andino (versión original de 1400 px; el epígrafe de esa foto nombra los tres aviones y el Mirage es el de alas en delta). No se encontró ninguna foto publicada del MS 760 de la plaza: se muestra otro MS 760 expuesto en una rotonda de Mendoza (Wikimedia Commons, Jorge Souto, CC BY-SA 3.0) con la nota visible "Foto ilustrativa: es otro MS 760 expuesto en Mendoza, no el de la plaza". Reemplazar por una foto propia cuando se visite el lugar.
- Más contenido en Coquimbito (`coq`): tres piezas nuevas además de los 649 puntos. "Lo decidieron los vecinos" (los 4 pasos del PAR, con foto aérea de Cristian Lozano / Sitio Andino y una imagen del acto de 2021 de Mendoza Post), "Una noche de vigilia" (tarde, medianoche y mañana del homenaje de 2024, con foto nocturna de Sitio Andino) y "Visitá el Museo Malvinas" (objetos, dirección Patricias Argentinas y Presidente Sarmiento, horario y botón "Cómo llegar", con foto de Los Andes). Los datos del museo (horario, dirección, maquetas del ARA Santa Fe y del destructor Rosales, cenotafio) salen de Los Andes, 16/7/2026, ya citado como fuente del lugar; se muestran con la nota "Confirmalos antes de ir". Varias piezas pueden ir tras la misma parte y quedan en el orden declarado. La línea de tiempo acepta pasos con texto (`label`) y foto, además de años.
- Corrección "Próximo lugar": usar solo el más cercano entre los lugares sin huella hacía rebotar entre el Memorial y Plaza Héroes a quien solo leía (sin escanear ninguno queda visitado) y nunca llevaba a Coquimbito. Se mantiene la cercanía y nunca se propone un lugar con huella; además, entre los que faltan se prefieren los que todavía no se abrieron en esta visita (`sessionStorage`, se olvida al cerrar el navegador). Si ya se abrieron todos, vuelve al más cercano. `nextStopFrom` en `web/src/lib/route.js`, con tests.
- Auditoría Stellar oficial: se corrigieron solo brechas baratas y seguras antes del pitch: timeout/backoff en lecturas Horizon, recuperación por hash tras errores ambiguos de submit, validación previa de saldo USDC y validación estricta de `USDC_MODE`. No se cambiaron formas de respuesta ni se agregaron operaciones Soroban.
- SEP-1: `/.well-known/stellar.toml` se sirve desde la propia API y declara HUELLA como asset `test` no redimible; la organización queda explícitamente marcada como cuenta de demostración sin aval institucional. `npm run home-domain` queda disponible pero no se ejecutó porque modifica la cuenta issuer y el hostname Railway de desarrollo puede exceder el límite de 32 bytes.
- Fees Stellar: se conservan fees fijas de testnet (100 stroops/op inner, 1000 stroops/op outer y operaciones patrocinadas) porque son techos compatibles con el fee-bump 10× y agregar `feeStats` dinámico suma una dependencia de red antes de cada firma; se documenta como mejora futura junto con clawback, SEP-24 y endurecimiento de wallet.
